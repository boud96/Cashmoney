# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Cashmoney is a local-first personal finance app for Windows and Linux: a Django + SQLite backend serves a JSON API and a React (Vite) SPA, and an Electron shell packages both into an installable desktop app. Users import bank CSVs, auto-categorize transactions with keyword rules, and review spending on a dashboard. Everything runs on `127.0.0.1`; there are no accounts or cloud services.

Session handoffs are in `.claude/handoffs/` (newest first). `.claude/notes/` holds finer product decisions, UI preferences, manual test checklists and the ideas list. `.claude/reviews/code_review_2026-10-11.md` is the current review and open-findings backlog (CR-n and BP#n numbers; older review files are kept for history). `.claude/tools/` has a headless-Chrome UI check harness and dev-DB analysis scripts (see its README). The whole `.claude/` directory is gitignored, so these files exist only locally.

## Commands

The dev tooling is Windows `.bat` scripts at the repo root (Linux twins below). Python is always `.venv\Scripts\python.exe`. Node comes from `PATH`, or from the portable copy in `tools\node` (`node.bat` / `npm.bat` wrap it).

```powershell
.\setup_dev.bat                 # create .venv, pip install backend/requirements.txt, npm ci frontend+desktop (if missing)
.\run_app.bat                   # setup + migrate + build frontend + runserver :8000 + open Electron (or browser)
.\build_frontend.bat --skip-setup   # Vite build into backend\finance\static\finance\react\
.\build_packaged_app.bat        # frontend + PyInstaller backend (pinned in backend\requirements-build.txt) + electron-builder -> desktop\dist\
.\node.bat --check desktop\main.js  # Electron syntax check
```

Linux has bash twins of the main scripts: `./setup_dev.sh`, `./run_app.sh [Electron args]`, `./build_frontend.sh [--skip-setup]`, `./build_packaged_app.sh` (→ `desktop/dist/cashmoney_<version>_amd64.deb`, `Cashmoney-<version>.AppImage`). There Python is `.venv/bin/python`, and Node 24 must be installed (no portable copy; `setup_dev.sh` refuses a Windows npm seen through WSL). Keep each `.bat`/`.sh` pair in step. A new `.sh` gets LF endings (`.gitattributes`) and `git add --chmod=+x`; CI runs `shellcheck` on them. `run_app.sh` opens the browser where Electron's sandbox can't start from `node_modules` (stock Ubuntu 24.04+).

Backend (run from `backend\`):

```powershell
..\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
..\.venv\Scripts\python.exe manage.py test finance                                   # all tests
..\.venv\Scripts\python.exe manage.py test finance.tests.test_transactions           # one module
..\.venv\Scripts\python.exe manage.py test finance.tests.test_transactions.TransactionAPITests.test_some_method   # one test
..\.venv\Scripts\python.exe manage.py seed_sample_data --if-empty
```

Backend tests are in the `backend/finance/tests/` package, one module per area: `test_transactions`, `test_definitions`, `test_imports`, `test_camt053`, `test_categorization`, `test_dashboard`, `test_exchange_rates`, `test_maintenance`, `test_api_requests` (errors, CSRF, origins, limits, CSP, health), `test_admin` (the Django admin and how it opens), and smaller ones for models, sample data, settings and migrations. `base.py` has `FinanceTestCase` (sample definitions plus `post_json`/`patch_json`/`delete_json` and transfer helpers) and `json_body`; most test classes build on it.

Lint/format: ruff via `.pre-commit-config.yaml` (`ruff-check --fix`, `ruff-format`; hook revisions are frozen to commit SHAs). `ruff.toml` keeps the rule set at E4/E7/E9/F, because newer ruff enables far more rules by default; add rules deliberately. Ruff is not in `requirements.txt`. The frontend has `npm run lint` (ESLint; it catches undefined names, which the build doesn't, plus the hooks rules; the existing `exhaustive-deps` warnings are known) and `npm test` (Vitest, `src/*.test.js`, currently `shared.js` helpers). Run both from `frontend/` and build. `npm run lint` also covers `frontend/scripts/`. `desktop/` has `npm test` (`node --test`, for `backend-support.js`). CI runs all of them and the backend tests before the build, and after the packaged build runs `frontend/scripts/ui-smoke.mjs`: headless Chrome against the PyInstaller backend, every page, no console errors. The Linux job runs the backend and desktop tests on Linux too, then the same smoke test attached to the installed app's own window (`CHROME_DEBUG_PORT`). Locally, still check UI changes in a browser (`.claude/tools/ui-check/`).

There is no Vite dev-server proxy. `api.js` calls `/api` on the page's own origin, so the normal loop is: build the frontend, then load it from Django at `:8000`.

## Architecture

**Backend (`backend/`, single Django app `finance`)**
- `cashmoney_backend/settings.py` ignores the root `.env`. The DB is `DATA_DIR/db.sqlite3`, where `DATA_DIR = $CASHMONEY_DATA_DIR` or `backend/`. `DEBUG` comes from `CASHMONEY_DEBUG` (on unless set to `0`; the packaged app turns it off). `SECRET_KEY` is per install, kept in `DATA_DIR/secret_key.txt` (gitignored; `CASHMONEY_SECRET_KEY` overrides). WhiteNoise serves static files straight from the app folders. Time zone is `Europe/Prague`. SQLite runs with `transaction_mode: IMMEDIATE` and a 20 s `timeout`: with deferred transactions, a write that had already read failed at once while another request was writing (`.claude/tools/analysis/lock_check.py` reproduces it).
- `views.py`: the API is hand-rolled class-based views that subclass `JsonView`, not DRF. `JsonView.dispatch` turns exceptions into JSON errors: `APIValidationError(message, details)`, `KeyError`, `ValueError` and a model's `ValidationError` → 400, `IntegrityError` → 409, `Http404` → 404. Validation therefore works by raising; don't build error responses by hand. Request bodies go through `parse_json_body`, and responses through `json_response` plus the `serialize_*` helpers in `serializers.py`.
- The API validates input itself, but the Django admin and scripts reach the models directly, so models with currency fields or `owners` use `CheckedValuesMixin` (`models.py`): `clean()` reports bad values on admin form fields and `save()` refuses them (three-letter codes, with the aliases in `constants.CURRENCY_ALIASES`; at least one owner). A new currency field goes in the model's `currency_defaults`.
- `services.py` holds the domain logic: CSV decoding/dialect/column detection and import, `CategorizationService` (active keywords by priority, include/exclude terms, targets subcategory/tags/WNI/ignored), Frankfurter exchange rates cached in `ExchangeRate`, ORM-aggregated dashboard summaries, and internal-transfer matching. Provider calls run inside requests, so they time out after 5 s, a network failure skips the provider for 5 minutes (the explicit sync retries at once), and the currency list is cached for a day. An import that imports nothing (every row failed, an empty or unreadable file) answers 400 with its report and keeps no `CSVImport`; reports list at most 100 failed rows (`skipped.error_count` has the total). Duplicates match on `original_id` per account, or without one by count of identical rows. `statement_parsers.py` splits a camt.053 batch entry into one row per payment when it can; those rows keep `batch_original_id`/`batch_amount` so the duplicate check also recognizes a batch that versions up to 0.8.0 imported as one row. Keep that check if the IDs change.
- Transaction search ignores case, accents and punctuation: `search.py` `fold_search_text` is a SQLite function plus the `searchfold` lookup, registered in `models.py`. Keyword matching ignores whitespace, case and accents but keeps punctuation (`normalize_keyword_text` in `services.py`). Filter semantics live only in `filtered_transactions`; after a row edit the PATCH response carries `matches_filters`, which the dashboard uses to keep an edited-out row highlighted. Checklist filters have pseudo values: `__unassigned__` (e.g. Untagged), `__none__` (nothing selected) and, for tags only, `__any__` (Tagged).
- `AppShellView` serves `templates/finance/app.html` and finds the hashed React bundle through the Vite manifest at `finance/static/finance/react/.vite/manifest.json`. That directory is generated and gitignored; never edit it by hand. `app.html` sets a Content-Security-Policy (`<meta>`): only same-origin scripts, styles (`'unsafe-inline'` for AG Grid and Plotly), images, fonts and requests. Anything new from elsewhere must be added there; check the console for "Refused to …".
- `packaged_backend.py` is the PyInstaller entry point. It sets `CASHMONEY_DEBUG=0`, runs migrations, seeds sample data only if the DB is empty, then serves the app with waitress on `$CASHMONEY_PORT`. `backend.log` rotates at 1 MB. On POSIX it makes the data folder private (0700), and when the desktop app passes its PID (`CASHMONEY_APP_PID`), `watch_parent` exits the backend once the app is gone (a crash or `kill -9` must not leave port 8765 busy; Windows ends a leftover from the app instead). `run_app.bat`/`run_app.sh` keep using `runserver` for development.
- PyInstaller's Django hook bundles any `*.db`/`db.*` file next to `manage.py`, such as the dev database (CR-60). `cashmoney-backend.spec` drops those, and both build scripts run `check_bundle.py` on the finished bundle and fail if a database file got in.
- Maintenance endpoints (backup/restore/delete) require exact confirmation phrases (e.g. `RESTORE DATABASE`). A restore makes a pre-restore backup and then migrates, so schema changes must keep older SQLite backups restorable; a backup with migrations this version doesn't know is refused. Restores and "Delete all" save safety backups in `DATA_DIR/backups/`; `prune_safety_backups` then keeps the newest 10 of that kind plus any from the last 90 days, and never touches files it didn't name.
- The Django admin has no password (`admin_site.py`; its `CashmoneyAdminConfig` replaces `django.contrib.admin` in `INSTALLED_APPS`). Maintenance → Advanced → Open database admin posts to `/api/maintenance/admin-session/`, which signs that browser in as the built-in `cashmoney` superuser (unusable password) and opens `/admin/` in a new window. `has_permission` also needs the session's `BACKEND_RUN_ID`, so a sign-in ends when the backend restarts (the desktop app closes; in dev, every runserver reload). `/admin/login/` only says where to open it from, so `createsuperuser` users can't log in. Admin edits skip the app's logic: e.g. a changed amount doesn't update `converted_amount`.

**Frontend (`frontend/src/`)**
- `App.jsx` owns global state: reference data (accounts, mappings, categories, tags, keywords, settings), the dashboard summary and transactions, theme/accent/hide-amounts, toasts and confirm dialogs. Pages under `pages/` are lazy-loaded and get data and reload callbacks from it. It also keeps the dashboard's tab (Overview or Transactions, stored like the Definitions tab): the summary always loads, the transaction list only while the Transactions tab is open; after a change it reloads at once there, otherwise when that tab next opens.
- `api.js` is the only fetch layer (`apiGet`/`apiPost`/`apiPatch`/`apiDelete`). A failed request's error carries the JSON body as `error.payload`; when requests stop reaching the backend at all, it fires `BACKEND_REACHABILITY_EVENT` and App shows the offline banner.
- Put shared code in the shared modules instead of copying it into pages: formatting (`formatMoneyValue`, `formatCount`, …) and filter/chart/color helpers go in `shared.js`; UI primitives (`ModalShell`, `CloseButton`, `ConfirmDialog`, `HelpTooltip`, `Select`, `LoadingButton`, `Spinner`, `DateField`, `TagToggleList`, `Tabs`, `PopoverButton`, `FilePicker`, `useFillHeight`) are in `components.jsx`, and the inline SVG icons (`CloseIcon`, `PencilIcon`, `TrashIcon`, `ChevronIcon`, …) in `icons.jsx`. `TagToggleList` picks tags as pills in their colours (the Tag filter, Bulk assign, both keyword forms); the table's tag editor keeps its own popover. `DateField` is a YYYY-MM-DD text field with a calendar pop-up; it applies only complete, real dates (`parseDateInput`), so half-typed text never reaches the filters.
- The Dashboard's parts are in `pages/dashboard/` (`FilterBar`, `TotalsRow`, `OverviewCharts`, `TransactionToolbar`, `TransactionGrid`, `ActionDialogs`); `DashboardPage.jsx` holds their state and handlers. Once opened, the Transactions panel stays mounted and is only hidden (`hidden`, so `display: none`) while the Overview shows: the grid keeps its sort, scroll and highlights, and code that measures it (`useFillHeight`) must cope with a hidden element. Definitions are tabs, each a `DefinitionSection` whose search box filters its grid (`QuickFilterModule`). `frontend/scripts/ui-smoke.mjs` waits for the Overview's chart and category rows, then opens the Transactions tab and waits for table rows: keep it in step with the dashboard's tabs.
- The dashboard loads the summary and the transaction table separately. Table loads are delayed and debounced, and sequence refs drop stale responses. Transactions are capped at `limit=10000` (the backend maximum), and the UI warns when rows are left out. `raw_data` is not in list responses; it is fetched on demand from `/api/transactions/<id>/raw-data/`.
- AG Grid registers only the modules each grid uses (`pages/dashboard/TransactionGrid.jsx`, `DefinitionsPage.jsx`), not `AllCommunityModule`. A new grid feature needs its module: an editable text column needs `TextEditorModule`, for example. A missing one can fail silently, so register `ValidationModule` while checking a grid change (it names what's missing), then remove it. Plotly is the full `plotly.js-dist-min` on purpose: a custom bundle needs the `plotly.js` source package and its dependency tree for about 130 ms per launch.

**Desktop (`desktop/main.js`)**
- In dev, Electron loads `http://127.0.0.1:8000` (reusing a running dev server). When packaged, it starts the bundled backend exe on port 8765 with `CASHMONEY_DATA_DIR` set to Electron `userData`, so the DB and logs live there, plus a per-launch `CASHMONEY_INSTANCE_TOKEN` and its own PID (`CASHMONEY_APP_PID`). It only loads a backend that answers `/api/health/?nonce=…` with the HMAC of the nonce under that token (`backend-support.js`), ends a leftover `cashmoney-backend.exe` first (Windows only), and waits up to 120 s behind a "Starting Cashmoney…" page while the process runs. New desktop modules must be listed in `desktop/package.json` `build.files`.
- Per-platform file names come from `platformFiles()` (`backend-support.js`): `cashmoney-backend(.exe)`, the venv's `Scripts\python.exe` or `bin/python`, and `favicon.ico` or `desktop/assets/cashmoney.png` (Electron on Linux can't use an `.ico` window icon). `userData` is named after `package.json`'s `name` (no top-level `productName`): `%APPDATA%\cashmoney-desktop`, `~/.config/cashmoney-desktop`. Adding a `productName` would move existing users' data folder.
- Linux packages (`build.linux` in `desktop/package.json`): a `.deb` (package `cashmoney`, `/opt/Cashmoney`, `cashmoney.desktop`; electron-builder's post-install adds an AppArmor profile so the sandbox works on Ubuntu 24.04+) and an AppImage on toolset `appimage: "1.0.3"` (static runtime, no libfuse2; its launcher adds `--no-sandbox` only where user namespaces are blocked). That needs electron-builder ≥ 26.17. Our code never adds `--no-sandbox`.
- External HTTP(S) links open in the system browser; same-origin links (including `/admin/`) stay in the app.

**Versioning and releases**
- The product version comes from `desktop/package.json` and `desktop/package-lock.json`. `frontend/vite.config.js` reads the lockfile to show the version in Help → About, so run `npm install` in `desktop/` after a bump. `frontend/package.json`'s version is not the product version.
- `.github/workflows/build.yml` builds on PRs into `main` and `develop` (Dependabot opens the ones into `develop`) and on manual runs, not on pushes. Jobs: `build-windows`; `build-linux` on `ubuntu-24.04`, never `ubuntu-latest`, because the PyInstaller backend only runs on a glibc at least as new as the build machine's (24.04: Ubuntu 24.04+, Debian 13+, Fedora 40+). With user namespaces blocked as on a stock Ubuntu desktop, it starts the installed `.deb` and the AppImage under Xvfb for the smoke test and checks that killing the app takes its backend down. Actions are pinned to commit SHAs with the release in a comment; `.github/dependabot.yml` proposes updates monthly, into `develop`. A pushed `vX.Y.Z` tag publishes `Cashmoney-Setup.exe`, `Cashmoney-Portable.exe`, `Cashmoney-amd64.deb`, `Cashmoney-x86_64.AppImage` and `checksums.txt` (written by the separate `publish-release` job over all four; the build jobs have read-only access); README download links depend on those names. To release, merge to `main`, then tag that exact `main` commit.
- Git flow: feature work on `develop` → PR to `main`.

## Project-specific rules

- The Django admin opens only through Maintenance → Advanced (`/api/maintenance/admin-session/`), without a password. Never add admin passwords, default credentials, a login form or another way to sign in.
- The donation panel appears only in Help → About. It is enabled by the build-time `VITE_CASHMONEY_DONATION_URL` (a public Stripe Payment Link set as a GitHub repo *Variable*). Keep the copy short and factual, never add Stripe secrets, and never add floating widgets.
- UI conventions: dashboard action buttons use `link-button`. Explanatory text goes under modal titles. Empty tag cells show no placeholder pills. Edits update grid rows in place (no full reload or scroll-to-top); a row edited out of the active filters stays visible, highlighted, until the next refresh. Follow the existing card/form CSS patterns in `styles.css`, because mid-width layout overlap has been a past problem.
- Keyboard focus: a busy `LoadingButton` stays focusable (`aria-disabled`) so focus can return to it after a dialog; only busy submit buttons are disabled. AG Grid `columnDefs` must not depend on callbacks that change every render (the Definitions grids read theirs through a ref): new columns rebuild the cells and drop focus.
- Money is stored as `Decimal`, and the API sends it as two-place decimal strings (`"-12.50"`, `serializers.money()`). Never send money as floats. The frontend converts with `Number()` only at the edges: the formatters, chart inputs, and the grid's `compareAmounts`. SQLite stores whole amounts as integers, so SQL arithmetic on amounts must not divide integers (see the owner split in `build_dashboard_summary`).
- The root `.env`, root `db.sqlite3`, and the `docker`/`llm-categorization` branches belong to the old pre-rewrite Streamlit/Postgres app. The current app doesn't use them or Docker.
- `data/` (gitignored) and stray bank exports at the repo root (e.g. `creditasone*`, which are not ignored) contain real personal bank data. Never commit them.
